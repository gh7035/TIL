# @Version 어노테이션?

비관적 Lock / 낙관적 Lock 중 낙관적 Lock에 속하는 어노테이션이다.

### 낙관적 Lock 이란?
충돌이 자주 일어나지 않을 것을 전제로 사용하고, 데이터를 읽을 때 DB에 락을 걸지 않는다.
대신 _수정하는 시점에_ 내가 읽은 뒤로 다른 트랜잭션이 이 데이터를 바꿨는지 확인하는 것이다.
DB 락이 아니라 애플리케이션 레벨에서 충돌을 감지하는 방식이라 볼수있다.

### @Version 동작 방식

```java
@Entity
public class TeamProject {
    @Id @GeneratedValue
    private Long id;

    private String description;  // 여러 팀원이 동시에 수정할 수 있는 필드

    @Version
    private Long version;
}
```

엔티티를 수정하면 JPA가 UPDATE 쿼리에 version 조건을 자동으로 붙인다.

```sql
UPDATE team_project
SET description = ?, version = version + 1
WHERE id = ? AND version = ?   -- 내가 읽었을 때의 version
```

- 그 사이 아무도 수정하지 않았다면 → version이 일치해서 1건 수정되고, version이 1 오른다.
- 다른 트랜잭션이 먼저 수정했다면 → version이 이미 올라가 있어서 update 쿼리가 취소되고, 예외가 발생한다.
  - JPA: `OptimisticLockException`
  - Spring: `ObjectOptimisticLockingFailureException`

### 주의할 점

- version 필드는 직접 수정하지 않는다. JPA가 관리한다.
- 사용할 수 있는 타입: `int`, `Integer`, `long`, `Long`, `short`, `Short`, `Timestamp`
- **JPQL 벌크 연산(`@Modifying` UPDATE)은 version을 올리지 않는다.** 필요하면 쿼리에 `version = version + 1`을 직접 넣어야 한다.
- 예외가 나면 재시도할지, 사용자에게 다시 시도하라고 안내할지는 직접 처리해야 한다.

### 비관적 Lock과 비교

| | 낙관적 Lock | 비관적 Lock |
|---|---|---|
| 전제 | 충돌이 드물다 | 충돌이 잦다 |
| 방식 | 수정 시점에 version으로 충돌 감지 | 읽을 때부터 DB 락 (`SELECT ... FOR UPDATE`) |
| JPA | `@Version` | `@Lock(LockModeType.PESSIMISTIC_WRITE)` |
| 충돌 시 | 예외 발생, 후처리 필요 | 다른 트랜잭션이 대기 |
| 단점 | 충돌이 잦으면 재시도 비용이 커진다 | 대기·데드락 위험, 처리량 저하 |
